## Contract and implementation

HnApplicationWindow supplies live inherited appearance defaults to existing and
light-created native controls in Holonight and Fusion. Add HnWindowPalette to
Holonight.Core as implementation support with a target `window` property, not an
application palette-selection API. It uses the engine AppearanceReader,
ThemeResolver and buildPalette. Explicit application roles resolve over appearance
defaults; QQuickPalette::inheritPalette preserves explicit window/control/group
roles. Never repeatedly assign a full window palette or set the application palette.

Observe appearance, window palette and ApplicationPaletteChange; guard reentrancy
and queue application-event refreshes after Qt propagation. Retargeting/destruction
must detach target connections/event filters safely. Private QuickPrivate linkage
uses the existing Qt dependency; no Controls, Templates or style imports in Core.
No platform-theme policy, standard style, composite or AI source changes.

### Behavior and compatibility

`qml/hnwindowpalette.{h,cpp}` observes the engine reader and applies inherited
window defaults. `qml/CMakeLists.txt` registers it in Core with private QuickPrivate
linkage; `qml/HnApplicationWindow.qml` instantiates it. The usage guide documents
its implementation-only role. The existing window/frame API is unchanged.

One Qt resolve detail is essential: `QPalette::resolve()` retains its left-hand
mask, even when colors came from the right-hand defaults. After resolving explicit
application roles over buildPalette, the bridge unions the two masks on the
**inherited value**. This lets appearance roles propagate without putting them in
the window's requested palette. The first implementation without this mask union
failed the regressions; the final one preserves partial and full overrides and
restores inheritance on reset. No production `QGuiApplication::setPalette()` call.

Seven WindowPalette regressions run in four independent style/DPR processes.
They cover existing and light-created controls; Active/Inactive/Disabled roles;
window Base and Disabled/Text overrides; complete window palettes; control Base
and Disabled/Text overrides; explicit partial/full application palettes and reset;
background and rendered sample round-trips; and explicit shared-composite palette
bindings. CoreIsolation additionally exercises null targets, retargeting, target
and helper destruction, queued callbacks, and absence of Controls/style modules.
Installed-package acceptance includes the new tests in both styles.

Shared composites retain their existing appearance-owned palette bindings. An
explicit `palette: Palette { base: ... }` replaces that binding and inherits
unspecified roles from the window. An imperative mutation of a role on their
existing appearance-bound palette can still be replaced by the next appearance
update; the initial test exposed that pre-existing distinction, and was corrected
to exercise the explicit palette-binding override. No composite source changed.
Native controls retain single-role overrides across transitions.
