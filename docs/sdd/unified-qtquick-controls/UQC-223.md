## Finding and owner

**Reading `QQuickWindow::contentItem()->palette` creates a stale inheritance
boundary. Activation then propagates its construction palette to descendants.**
The retained palette observer performs precisely this allocating getter while
walking every QObject/visual item (`audit/palette-diagnostics.cpp`, lines 77–81).
The original transition collector also reads every item's palette. Neither read
is observationally neutral, despite avoiding deferred control implementations.

The corrected *diagnostic recorder* checks `QQuickItemPrivate::providesPalette()`
before reading existing palettes. It has an explicit `--content-palette read`
experiment that performs the offending getter once per window. `passive` omits
that intervention. The retained observer, original kits and archives are unchanged.
This is diagnostic instrumentation, not a production palette fix.

A dark-created main and secondary window both change to light successfully.
On activation/deactivation, with no appearance revision or file change, native
Button/TextField/SpinBox/ComboBox palettes return to their dark construction roles.
The window itself stays light. Conversely, a secondary first created in light
successfully changes to dark, then returns to light on deactivation. Its native
TextField fill sample changes from `#ff131a24` to `#fff1f5fa`; the root content-item
palette remains light. Shared search/combo retain appearance-owned colors.
All 16 shared-window activation cases with the getter fail; all 16 passive
counterparts pass, across default/Fusion, DPR 1/1.25, both construction histories,
and two independent runs per combination. Repeated role failures and text-fill
samples match exactly (16 repeat pairs, including passing comparisons).

The initial light-created-window experiment also exposes main-window reversal
while the new secondary is shown: offscreen exposure changes activation. The
`beforeSecondaryPrimary` snapshot separately proves the successful main transition
before that event. Do not attribute it to creating QML controls alone.

The immediate responsible boundary is **Qt Quick root-content-item palette
propagation, exposed by the provider-owned diagnostic observer**. The bounded
next repair owner is the provider's audit instrumentation. No AI or consumer
repair is established, and no production HnWindowPalette repair is justified by
this observed-only failure. A Qt mitigation/upstream handoff is a separate choice.

## Mechanism and source inspection

- `qml/hnwindowpalette.cpp` refreshes inherited window defaults from the reader,
  preserving requested roles; application events schedule a guarded refresh.
  Recorded window palettes remain current while descendant palettes reverse.
- Qt `QQuickWindowPrivate::updateChildrenPalettes()` propagates to children of
  `contentItem()`, skipping the content item itself. An allocated root palette
  therefore retains its previous colors.
- Installed Qt 6.11.2 private headers show lazy allocation in
  `QQuickPaletteProviderPrivateBase::palette()`. `setCurrentColorGroup()` calls
  `QQuickPalette::setCurrentGroup()`, whose `changed()` signal propagates its
  palette to descendants. Window activation/deactivation traverses the root item.
  Equal Active/Inactive role colors do not prevent this propagation: changing the
  selected group still emits the signal.
- `qml/controlpalette.cpp` resolves source roles and appearance fallback but does
  not own the stale parent. Appearance-bound composites stay current.
- `src/platformtheme/holonighttheme.cpp` initializes its palette from startup
  configuration without connecting live palette updates. However, clearing that
  plugin still reproduces the getter-induced shared-window activation failure;
  its static startup palette is not the necessary trigger.

Qt source inspected from the upstream [6.11 window implementation](https://github.com/qt/qtdeclarative/blob/6.11/src/quick/items/qquickwindow.cpp),
[item implementation](https://github.com/qt/qtdeclarative/blob/6.11/src/quick/items/qquickitem.cpp),
and [palette implementation](https://github.com/qt/qtdeclarative/blob/6.11/src/quick/items/qquickpalette.cpp).
These branch sources support the installed-header/runtime evidence, not a claim
that the distribution binary was built from that exact branch head. Download
hashes are retained in [the result summary](audit/uqc223-results.json).

## Diagnostic implementation and results

`audit/palette-transition.cpp` adds an opt-in offscreen-only interaction path.
It records requested appearance text, reader revision, stable object identity,
all Active/Inactive/Disabled roles and resolve masks, current color group,
activation/focus/hover/application events, background colors and rendered samples.
Immediate snapshots precede frame capture; settled palette/fill observations use
an exposed-window frame boundary, not long sleeps. Button animation pixels remain
informational; the rendered reversal assertion uses native TextField fill.

Each process tests one intervention: activation, direct hover entry/exit, Link-role
mutation/reset (palette re-resolution), ApplicationPaletteChange, or enabled-state
change. Synthetic input is guarded by the offscreen platform check; no real
pointer, desktop focus, VT or user session is touched. Both windows and controls
are named; the dark-created secondary is a separate process history. Collection
errors and behavioral failures remain separate. Nothing is added to ordinary CTest.

`palette-stability.py collect` runs the bounded 74-process matrix;
`assert` deliberately exits 1 on this unchanged production baseline. It rejects
incomplete matrix collections. [Compact results](audit/uqc223-results.json) retain
case counts; raw measurements/events/PNGs/maps/commands/experiment configuration
are under umbrella `.cache/uqc223/matrix/`.

## Proposed regression and repair contract

   including root items. Record `paletteAllocated` without causing allocation;
   observe activation/hover and appearance revisions without changing them.
   Add an observer-on/off equivalence regression that checks allocation and the
   post-transition activation sequence. Preserve old observer binaries/evidence.

   diagnostic. Any separately approved Qt workaround must preserve requested
   application/window/control roles, all groups, resets, appearance-bound shared
   composites, Core isolation and both light/dark construction histories. Never
   mask the result by assigning full control palettes or changing consumers.
3. Require stable named-control roles and rendered fill at unchanged scheme/revision
   through activation/deactivation in both styles at DPR 1 and 1.25. Passive
   collection must not manufacture the stale root, and repeat processes must agree.
4. After a separately verified instrumentation repair, request only affected human
   palette-stability checks and missing fresh Fusion light-time Settings creation.
