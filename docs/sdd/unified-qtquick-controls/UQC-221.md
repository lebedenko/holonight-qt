## Proven diagnosis — 2026-09-17

Assignment checkpoint: umbrella `d517c4d`, created before diagnostic implementation.
Diagnosis owner is **holonight-qt shared-window palette propagation**. AI contains
no necessary trigger: the same mismatch occurs in a plain Window. The provider
window binds `color` to the live Core singleton but leaves its Qt palette inherited
from the startup application/platform palette. `HoloniightTheme` constructs
`palette_` once and never connects its reader's paletteChanged signal. In contrast,
`ControlPalette::componentComplete()` observes the engine appearance reader;
HnSearchField and HnIconComboBox bind their palettes to that live value.

This proves the missing bridge, not a mandate to make platform-theme policy live
application-wide. No production change was made. Native controls in **both**
styles reproduce the missing file transition. This extends automated evidence;
it does not revoke the user's accepted HoloNight interaction checks or claim a
new manual failure.

Fusion controls cannot handle live palette changes. Preserve the native-only
fixture for an upstream report or Qt-version comparison; no upstream fix is
claimed or required for this diagnosis handoff.

## Repair proposal: UQC-222 (not implemented)

Owner: holonight-qt. Establish a **window-scoped live default palette** for
HnApplicationWindow, sourced from its engine's appearance reader, using the same
full-role palette construction as shared composites. Bind the Window palette,
not individual field backgrounds. Keep the primitive Core-only: expose the
required QPalette value through a Core-safe bridge rather than importing Controls
or the Controls-dependent implementation module into Core. Review the precise
bridge surface in the repair SDD before assigning implementation.

Intended behavior: existing and newly constructed HnApplicationWindow children
inherit the current appearance palette immediately in either style. Preserve
explicit window, control and color-group overrides through Qt resolve semantics;
keep disabled roles distinct and retain shared-composite behavior. Plain external
Qt windows and application-wide palette policy remain outside this contract.
A platform-theme broadcast alone is a broader policy change and does not establish
the newly-created-window contract demonstrated above.

Exact regression coverage required before accepting a repair:

1. File-driven dark/light/dark native TextField, SpinBox and ComboBox in
   HnApplicationWindow, both styles and DPR 1/1.25; palette roles, backgrounds and
   interior pixels must change consistently. Existing and light-recreated windows
   must agree. Preserve the plain Window diagnostic as the boundary comparison.
2. Full window palette override, single control Base override, Disabled-group
   override and disabled native controls; unrelated roles continue inheriting.
3. Shared HnSearchField/HnIconComboBox file propagation and local override behavior;
   native Fusion appearance, explicit style selection and embedded defaults.
4. Core-isolation process, registered palette/composite/import checks. Retain the
   provider-free recreation failure separately so a provider repair cannot
   accidentally claim to fix Qt's external initialization behavior.

No AI implementation package is needed for the proven native-input defect. The
broad ComboBox observation remains qualified by the object-level evidence above.
No repair kit, new public API, schema or dependency change is part of UQC-221.
