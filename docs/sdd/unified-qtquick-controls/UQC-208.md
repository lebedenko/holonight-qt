## Reproduction and ownership contract

At scale 1, in a logged-out isolated NeoChat profile, open Settings → General →
Appearance → close Settings, three times without choosing a scheme. Compare
Tokodon, whose Settings opens on Appearance. Repeat HoloNight/Fusion from identical
initial profile and palette state, and confirm any symptom without instrumentation.
Only humans operate actual application navigation; do not automate pointer/focus.

Capture application, window and existing control palette roles, resolve masks,
active/inactive/disabled groups and alpha, palette-change events, selection state
and loaded origins. Observers must neither instantiate deferred controls nor write
palette state. Inspect Quick style updates, QStyle/platform palette paths and
application scheme-selection code before assigning ownership.

Inspect Haruna file/color pickers and Tokodon font picker before and after the
transition. Identify the actual native/widget/Quick backend and concrete control
origins. Similar appearance alone is not backend or provider ownership evidence.

For a demonstrated provider defect, add a deterministic failing regression first
and make the smallest repair. Preserve explicit application/window/control roles,
alpha, groups, appearance reload, sibling/window isolation and picker reopening.
No public API or dependency changes. If the focused sequence and confirming
comparison leave reproduction or ownership unresolved, record the evidence and
stop speculative repair. External defects need an owner-specific follow-up, not
an application patch in this iteration.

Run focused palette/regression checks before the full provider suite and applicable

existing harness; check restoration, hashes, staged modules, indexing and outcomes.
Manual acceptance is limited to these palette/navigation/picker paths at scale 1;
fractional scale is added only if evidence implicates it.

UQC-208 closes only when scoped acceptance is satisfied. UQC-201 stays In Progress
and the initiative Accepted. Preserve unrelated accepted results. Settings/AI

## Implementation

The demonstrated provider-owned P02 cause is an omitted `QPalette::Light` fill.
Map it to the existing `surfaceRaised` token in Active and Disabled; Inactive
inherits Active. No palette-update or application-selection code is changed.
The external P01 activation path receives an owner-specific follow-up in findings.

Changed files: `palette/palette.cpp`, `tests/test_palette_qpalette.cpp`,
`tests/test_quick_palette.cpp`, `tests/RuntimeComposites.cmake` and the audit-only
`palette-diagnostics.cpp` / `check-palette-diagnostics.cpp`. The opt-in observer
captures existing objects and resolved palettes; it is not installed as a product
plugin. Its separate build artifact is staged only in the acceptance kit.

Regression coverage includes every scheme/color group, all three installed Qt
fallback picker implementations, dark/light/dark transitions, translucent local
overrides and picker reopening. Control construction/destruction preserves the
application palette. Existing override, isolation and appearance-reload coverage
remains active. The observer checks both styles with instrumentation on/off and
asserts no deferred popup creation or palette/mask mutation.

Canonical reproduction, source attribution, failed-before evidence, verification,
limitations and kit handoff are recorded once in [Batch 4 findings](../../../../docs/initiatives/unified-qtquick-controls/FINDINGS.md#batch-4-palette-investigation-and-repair--2026-09-14).
Actual-app backend/navigation/picker acceptance is pending; do not mark Done.
